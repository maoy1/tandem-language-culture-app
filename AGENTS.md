# Mandatory project constraints

- Production runs only in SharePoint and the associated Power Apps / Power Automate services covered by existing organisational entitlements.
- No additional budget: do not introduce paid hosting, Azure Functions, external APIs/services, premium/custom connectors, new paid licences or trials as an implementation dependency.
- No Python server, local computer, scheduled local script or separately hosted runtime may be required by the deployed participant workflow. Python is permitted for optional local repository validation/tests only.
- This is a trusted internal app. Ordinary registration, updates, discovery, connection and group actions must be self-service, with admin effort kept low as participation grows. Routine operations must not depend on per-user approvals, individual grants, manual matching or manual user/group maintenance.
- Critical or exceptional cases may involve necessary admin approval, permission correction, assistance or intervention. Do not interpret self-service as a ban on admin support. Keep exceptions explicit and proportionate; do not add approval steps to every ordinary action. Existing identity and access requirements still apply.
- Before relying on any permission, setting, connection, connector, licence or configuration, flag it to the owner and verify availability in the actual tenant. Stop the dependent change if it is unverified; do not silently propose a paid workaround.
- Distinguish one-time setup and exceptional maintenance from routine participant actions. Flag necessary admin work upfront; do not promise zero operational maintenance.
- Work one ticket per branch/PR. Update current design, implementation plan and issue evidence together. Keep issues open until their acceptance criteria and relevant tenant tests pass.
- Current owner priority: build the integrated Power Apps/Power Automate path through discovery, in-app requests, group/membership actions and notifications before resuming the remaining detailed tests. Preserve prior results and defer unexecuted acceptance; do not close incomplete tickets or claim wider-release readiness. Use batched build guidance. Postpone setup-automation investigation and notification-channel questions until those features are built. The owner prefers a central in-app experience; Approvals is an option to evaluate later, not an approved connector/channel.
- Ordinary-participant access testing is deferred by the owner; use owner/synthetic data meanwhile. Do not infer ordinary-user exposure from admin group permissions, or declare privacy verified without the test.
- The current implementation authority is docs/CURRENT_DESIGN.md; tandem_app and reference DOCX files are historical sources, not approval to change the design.

Reuse only if repurposed to a clear type/scope; transfer every old acceptance obligation when splitting/retiring. Work one focused ticket at a time. Reject an over-limit package and redesign first. Keep flat stages and headroom where practical. Do not assume child flows/Solutions are available; verify any extra dependency before proposing it.
