Design and #47 receipt scope
Cancellation has no editable payload and a request has at most one lifetime cancellation. Use deterministic cancel:{trustedParticipantId}:request:{requestId}, as explicitly allowed by the owner when the actual export arrived. This supersedes the provisional UUID interface; there is no UUID ParseJSON action or required new app argument. Target or caller changes derive a different identity. Same-request transport retries replay the immutable row decision. Server resolves current SharePoint user through Invoker, requires required/unique/indexed Participantaccount User metadata plus exactly one own profile, checks supplied ParticipantId against it, then checks request sender before revealing a terminal result or writing.

Pending-only CAS updates Status=Cancelled, ConnectionKey=history:request:{id}, WinningOperationKey=the deterministic key, OperationComplete=true together under the exact read ETag. It preserves Id, sender/recipient/group, RequestType, SendOperationKey and all other history fields. The request row is the bounded atomic decision receipt. No OperationReceipts list, group guard, member write, notification write, schema write or permission change is introduced. This is adequate only for this immutable one-row decision, and requires every consumer to preserve history/parties and forbid reopening. Cross-list acceptance and notification recovery remain their own contracts.

Pending and Accepted-incomplete retain canonical unique live keys: open:person:{minParticipantId}:{maxParticipantId} or open:group:{groupId}:participant:{senderId}. Declined/Cancelled and completed Accepted must have coherent completed/history/winner markers. Accepted-incomplete cannot be cancelled. Legacy/incomplete rows are preserved and explicitly rejected, never repaired. Cancellation does not require profile availability, group availability or membership reads. Send owns canonical UUID issuance; cancel requires durable nonblank unique SendOperationKey and exact preservation, without guessing #17's prefix.

Expected failure interpretation
- INVALID_INPUT/UNAUTHORIZED/REQUEST_SCHEMA_UNVERIFIED/read failure before write have no cancellation write attempt from this flow. Check writeattempted rather than inferring no effect from a generic failure.
- REQUEST_INTEGRITY after attempted CAS can mean a changed or malformed readback; outcomeunknown=true. Do not claim rollback or no effect.
- ALREADY_DECIDED and ACCEPTED_INCOMPLETE are truthful current outcomes, never cancel-success or overwrite targets.
- Red failed CAS/scope actions can be expected in a 412 race or recovered transport error. Inspect sanitized final response and exact persisted outcome, not run colour alone.
